# AiChat

This is the largest block in this design system (AiChat.tsx is still ~1,000 lines even after the split and the hook extraction below), so read this before touching anything here — it tells you which file actually owns the thing you're about to change. Paths below are relative to wherever this block was installed.

This is a directory guide, not full documentation for the block — it only covers what's specific to AiChat, not general conventions for whatever project it now lives in.

**On mobile (under 768px, `useIsMobile.ts`) the thread and slides panels open in a full-width `Drawer` instead of a resizable column.** Desktop is unchanged. `AiChat.tsx` builds each panel node once and places it in a `DesktopPanel` or a `MobilePanel` (`PanelSlot.tsx`). Both panels take `inDrawer`, which hides the expand button (the drawer is already full width) and leaves Escape to the Drawer; `DeckPanel` still stops Escape that belongs to the editor, so leaving a text box doesn't close the drawer. `expanded` is forced off on mobile.

**The chats sidebar collapses to a 64px rail on desktop and is a left `Drawer` on mobile.** `AiChat.tsx` passes `collapsible`, `collapsed` and `onCollapsedChange` to `Sidebar` only when not mobile (`railCollapsed`), and the Sidebar component hides the chat rows itself. The collapse toggle lives in the sidebar's header bar (`Sidebar` renders it), and while collapsed `Sidebar` drops the `SidebarHeader` content, so the new-chat and search buttons are repeated as icon-only buttons at the top of the body (`railCollapsed`), and the profile card shows just the avatar. The collapsed state is plain component state and isn't remembered across reloads. `SidebarSlot` wraps the Sidebar and supplies the mobile Drawer.

**Artifacts are data on the reply, like `deckEdit`.** A reply's `artifacts` (`ChatArtifact[]`: `id`, `kind`, `title`, `content`, optional `filename`) is stored on its message. `markdown` and `code` carry the text; `document` carries HTML (editable, see below); `pdf` and `image` carry a URL (a data URL works, so the demo needs no file hosting). Reusing an `id` in a later reply replaces that entry in the list. Artifacts on thread replies are stored but not shown: only the main pane renders cards (`renderArtifact`) and builds the list. The demo route's scripted replies live in `app/api/ai-chat/artifacts.ts` (docs-only, not shipped): "document" (or "doc", "word", "letter", "proposal"), "report" (markdown), "pdf", "image" and "html" in a message trigger them.

**A `document` artifact is editable and downloads as Word.** It opens in the `DocEditor` component (HTML content) inside the artifacts panel. Edits flow `DocEditor` → `ArtifactViewer.onChange` → `ArtifactsPanel.onArtifactChange` → `handleArtifactChange` in `AiChat.tsx`, which rewrites that artifact's `content` on its message, so reopening it, or the card, shows your edits. The viewer's header button builds a `.docx` in the browser (`downloadDocx`, via `jszip`); the editor's own download button is switched off there. The AI doesn't edit the text live like decks and sheets: a later reply with the same artifact `id` replaces the whole document, discarding the person's edits, so a real agent should be given the current content with each request. On mobile the panel is a bottom `Drawer` with a `DrawerHandle`, like slides.

**Ask AI from the slides panel adds a reference chip to the main composer.** `DeckPanel` passes `onAsk` to `DeckEditor`, which reports a `DeckAskContext` (the selected element, or the text highlighted inside one). `handleAskAboutSlide` in `AiChat.tsx` turns it into a `MessageAttachment` with `slideReference` (`messageHelpers.ts`): `name` is the chip ("Slide 2 · Title"), `detail` is what the model gets (deck id, slide id, element id and type, and the text). An attachment with a `detail` is a reference, not a file: `describeAttachments` skips it, and `buildPrompt` appends it as `Referring to …` after the typed text. Every place the prompt is built (`submit`, the new-chat path, `promptText` for history and regenerate) goes through `buildPrompt`, so references reach the model on later turns too. References live in `slideRefs` state next to `attachedFiles`, are cleared on send or when you switch chats, and only the main composer takes them. Desktop keeps the slides panel open and focuses the composer; mobile closes the sheet first.

**Either side panel can take the full width.** Dragging its handle 48px past `maxSize` (`ResizablePanel`'s `onSnap`) or pressing the expand button in its header sets `expandedKey` in `AiChat.tsx`. The chat column is then `display: none` and the handle is unmounted. The same header button (collapse icon, "Show chat") restores the split. Closing the panel also clears it. Because the chat column is hidden, refocusing its trigger after close waits a frame (`focusAfterClose`).

## Gotchas

**`useConversation` threads an explicit `id` through every action instead of reading a single "current" value.** Each call manages one pane (main chat, or the open thread), and each pane can have a reply in flight for a chat/thread the user has since navigated away from — switching chats doesn't cancel the old one's request, it just keeps running in the background and writes into the right place when it resolves. `submit`/`stop`/`regenerate`/`resendEdit`/`questionnaireAnswer` all take the chatId/threadId explicitly, captured by the caller at the moment the action was invoked, rather than reading `activeId`/`activeThread` (which can have moved on by the time a `.then()` fires). Don't "simplify" this by making an action read the pane's current id internally — that's exactly the bug this design avoids.

**Main chat and threads used to be two full, independently-maintained copies of send/stop/regenerate/edit logic — they're now one `useConversation` implementation, instantiated twice.** Before this, a fix or a new command (`/retry`, `/edit`, `/copy`) only reached the main pane unless someone remembered to also update the thread's copy. If you're about to write `if(isMainPane) { ... } else { /* same thing, for threads */ }` anywhere near a message list, it almost certainly belongs as a change to `useConversation.ts` instead, applying to both panes at once.

**`StreamingMessage`'s `key={m.versionIndex ?? 0}` in `MessageRow.tsx` is load-bearing, not decoration.** A regenerate keeps the same message `id` but produces new `text`. Without re-keying on `versionIndex`, `StreamingMessage` reuses its existing instance and its internal reveal-progress state carries over from the old text — it can already exceed the new text's segment count, so the new text renders fully revealed with no `StreamingSegment` ever mounting to call `onComplete`. Since `onComplete` is what flips `animate`/`isGenerating` back off, the message gets stuck showing as "still generating" forever. If you ever see a regenerated message stuck in that state, check whether something changed this key.

**`MessageActionsRow`'s action order is deliberate.** Copy always leads, regardless of sender — it's the one action every message gets. Refresh comes right after edit, ahead of the version-nav arrows it produces, so cause (regenerate) reads before effect (step through the resulting versions). The reply trigger is identified by a plain DOM `id` (`thread-trigger-${messageId}`), not a ref, so closing a thread can hand focus back with a simple `document.getElementById` lookup — the same approach `CommandPalette` uses for its active-option scroll-into-view.

**`ChatMessageRowContent` is genuinely shared, not copy-pasted, between the main pane and a thread.** A thread is just another list of the same `ChatMessage` shape, so the bubble/tool-call/questionnaire/streaming rendering only needs to exist once. The streaming-complete guard ("is this still the active streaming message?") lives in each pane's own `onStreamComplete` passed down as a prop, since the main pane and an open thread stream independently of each other — don't try to hoist that guard into `MessageRow.tsx` itself. `renderTrailing` and `editing` are only ever wired up by the main pane; a thread is a side conversation, not something you edit history in.

**A `null` `activeId` means "unsaved draft chat," and it collides with other `null`-initialized ids if you're not careful.** Each `useConversation` instance's `typingId`/`streamingId` both start as `null` before anything has ever generated. `isTyping`/`isGenerating` in `AiChat.tsx` guard with `activeId !== null &&` before comparing against `mainConversation.typingId` — without it, `null === null` would read as "typing" on every freshly opened draft chat, which is exactly the bug that shipped once before this guard existed. If you add another per-pane id-keyed comparison, give it the same guard.

**An attachment-only send has no text, but the API rejects an empty `message`.** `describeAttachments`/`promptText` in `messageHelpers.ts` exist so a message with files but no typed text still sends something meaningful (`"Attached: file.png"`) to the API and into history, while the chat bubble itself still shows just the attachment chips, no synthetic text. This applies everywhere a message's text is read for the API — send, regenerate, and history-building all go through `promptText`, not `m.text` directly.

**`types.ts` is re-exported from `AiChat.tsx`, not just defined there.** Your API routes and `ThreadPanel.tsx` import `ChatMessage`, `ChatEntry`, etc. from `AiChat.tsx`'s own path, not from `types.ts` directly — moving the type definitions into `types.ts` was an internal reorganization, and that import path had to keep working unchanged. If you add a new exported type to `types.ts` that anything outside this folder needs, add it to the `export type { ... } from './types'` line near the top of `AiChat.tsx` too, or code importing it from `AiChat.tsx` will fail.

**Deck edits are data (`DeckOp`s from the DeckEditor component's `ops.ts`), never a renderer or editor here.** Editing UI is the `DeckEditor` component; this block only decides whose changes land where.
- A reply's `deckEdit` lists steps. A `base` starts the deck over (a new document, with its undo history cleared); without one, the steps land on the chat's live document for that `deckId`.
- AI steps and your edits interleave freely. Every AI step goes through `applyOpsLenient`, so a step aimed at something you deleted is skipped and counted (the card and panel say how many), never thrown.
- Your undo applies your own inverse ops on top of whatever the AI has done since.
- `useConversation`'s `getDecks` sends the chat's live decks with every request as `{ deckId, deck }` pairs, so a real agent edits *your* version and can reply with a `deckEdit` for the same `deckId`. The demo route ignores them and its scripted steps use fixed ids.
- Every card for a deck opens the same live document, not a per-reply snapshot.
- New replies reach `AiChat.tsx` through `useConversation`'s `onReply` event, not an effect watching the message list.
- Closing the slides panel returns focus to the card's Open button by DOM id (`deck-open-${messageId}`), like the thread trigger.

**Sheet edits work exactly like deck edits, with `SheetOp`s and a `sheetEdit` on the reply.** A reply's `sheetEdit` (`{ sheetId, title, base?, steps }`) lands on the chat's live sheet for that `sheetId` (a `base` starts it over). Every step goes through `applySheetOpsLenient`, so a step aimed at cells you've since deleted is skipped and counted. Undo uses `diffSheets` inverse ops and reverts only your changes. `useConversation`'s `getSheets` sends the chat's live sheets as `{ sheetId, sheet }` pairs with every request, so a real agent edits your version; the demo route ignores them. Put `SHEET_REFERENCE` (exported by the SheetEditor component) in the agent's system prompt: it describes the ops, formulas and limits. Pick the step size by how it should read live: a row or column per step, not a cell. Ask AI in the sheet panel adds a reference chip (`sheetReference` in `messageHelpers.ts`: the sheet id, the range and the typed values) through the same `slideRefs` state as slides. Closing the panel returns focus to the card's Open button (`sheet-open-${messageId}`). The demo route's scripted sheet replies are `app/api/ai-chat/sheets.ts`: "spreadsheet", "sheet", "budget" or "excel" in a message builds one, and an edit request right after revises it.

**Don't add a settings-modal field "for completeness."** Four of them (response length, creativity, web search, sound) were added that way once and never wired to anything — each was read only by its own control, a closed loop contributing nothing. They were removed. `model`, `effort`, `displayName`, and `autoTitleEnabled` earn their keep (displayed elsewhere, or feeding real title logic) — if a new field can't say the same, it's decoration, not a feature. The one deliberate exception is the Connectors list: `enabledConnectors` is UI state only until you wire it to your backend (send the enabled ids with each message in `chatApi.ts`'s `sendMessage`). `model` and `effort` are likewise not sent to the API yet.
