# AiChat

This is the largest block in this design system (AiChat.tsx is still ~900 lines even after the split and the hook extraction below), so read this before touching anything here — it tells you which file actually owns the thing you're about to change. Paths below are relative to wherever this block was installed.

This is a directory guide, not full documentation for the block — it only covers what's specific to AiChat, not general conventions for whatever project it now lives in.

## File map

| File | What's in it | Edit this when you're... |
|---|---|---|
| `AiChat.tsx` | The orchestrator: UI-level state (which chat/thread is open, drafts, search, settings, the two delete/settings modals), two `useConversation` instances (one per pane), and the top-level JSX. No props — this is the block's single entry point. | ...wiring a new piece of UI into the layout, adding UI-level state, or changing which pane something belongs to. |
| `useConversation.ts` | The actual send/stop/regenerate/edit-and-resend/questionnaire-answer logic for *one* message list. Instantiated once for the main chat, once for the open thread. | ...changing how a reply is generated, regenerated, or resent — for both panes at once, since there's only one implementation now. |
| `types.ts` | Every shared interface/type (`ChatMessage`, `ChatEntry`, `AiChatReply`, `SearchHit`, etc.). Re-exported from `AiChat.tsx` so external code (your API routes, `ThreadPanel.tsx`) keeps importing from `AiChat.tsx`'s own path unchanged. | ...changing what a chat, message, or thread looks like. If you add a field here that a consumer needs, add it to the re-export list in `AiChat.tsx` too. |
| `icons.tsx` | The small inline SVG icon components (plus, pencil, trash, chevrons, etc.). Pure, no hooks. | ...adding or restyling an icon. Check here before drawing a new one — most common shapes already exist. |
| `constants.ts` | Pure data tables with no logic: the slash-`COMMANDS` list and the settings modal's `MODEL_OPTIONS`. | ...adding a command or a settings-modal select option. |
| `chatApi.ts` | Every `fetch` call this block makes (`fetchChats`, `fetchThread`, `sendMessage`, `searchMessages`), plus `buildSearchCorpus`. All of it talks to relative API routes (`/api/ai-chat/...`) — point these at your own backend. | ...changing what gets sent to or read from the API, or pointing this block at a real backend. |
| `messageHelpers.ts` | Pure functions over a message list with no React/DOM dependency: `buildHistory`, `findLastUserMessageId`, `hasPrecedingUserMessage`, `withVersion`, `describeAttachments`/`promptText`. Mostly consumed by `useConversation.ts` now, not `AiChat.tsx` directly. | ...changing how history is built for a reply, how "the latest user message" is found, or how versions (edit/regenerate) are recorded. |
| `MessageRow.tsx` | Everything about rendering *one* message: the bubble, the hover action row (copy/edit/regenerate/reply), the version nav arrows, the thread-reply pill, attachments, and the checkpoint divider. Shared by the main pane and `ThreadPanel`. | ...changing how a message looks or what actions it offers, in either the main pane or a thread — it's the same component for both. |
| `Composer.tsx` | The input bar: text field, slash commands, file/paste attachments, send/stop button. Shared by the main pane and `ThreadPanel`. | ...changing the input row itself, not what a message row looks like once sent. |
| `ThreadPanel.tsx` | The right-hand thread column's chrome (header, close button, scroll-to-bottom behavior) — the messages inside it still render via `MessageRow.tsx`. | ...changing the thread panel's own layout, not message rendering. |
| `StreamingMessage.tsx` | Renders one message's *text*: markdown, code blocks, charts, tables, the typewriter reveal. | ...adding a new fenced-block type (like `\`\`\`table`) or changing how text reveals while streaming. |
| `ChatMarkdown.tsx` | The `react-markdown` component overrides `StreamingMessage` renders through. | ...changing how a specific markdown element (a link, a list, inline code) looks. |
| `Phrases.tsx` | The random greeting on an empty chat and the rotating "Thinking…"-style typing phrases. Exports `USER_NAME`. | ...changing the greeting/typing copy, or the demo user's name. |

## Gotchas

**`useConversation` threads an explicit `id` through every action instead of reading a single "current" value.** Each call manages one pane (main chat, or the open thread), and each pane can have a reply in flight for a chat/thread the user has since navigated away from — switching chats doesn't cancel the old one's request, it just keeps running in the background and writes into the right place when it resolves. `submit`/`stop`/`regenerate`/`resendEdit`/`questionnaireAnswer` all take the chatId/threadId explicitly, captured by the caller at the moment the action was invoked, rather than reading `activeId`/`activeThread` (which can have moved on by the time a `.then()` fires). Don't "simplify" this by making an action read the pane's current id internally — that's exactly the bug this design avoids.

**Main chat and threads used to be two full, independently-maintained copies of send/stop/regenerate/edit logic — they're now one `useConversation` implementation, instantiated twice.** Before this, a fix or a new command (`/retry`, `/edit`, `/copy`) only reached the main pane unless someone remembered to also update the thread's copy. If you're about to write `if(isMainPane) { ... } else { /* same thing, for threads */ }` anywhere near a message list, it almost certainly belongs as a change to `useConversation.ts` instead, applying to both panes at once.

**`StreamingMessage`'s `key={m.versionIndex ?? 0}` in `MessageRow.tsx` is load-bearing, not decoration.** A regenerate keeps the same message `id` but produces new `text`. Without re-keying on `versionIndex`, `StreamingMessage` reuses its existing instance and its internal reveal-progress state carries over from the old text — it can already exceed the new text's segment count, so the new text renders fully revealed with no `StreamingSegment` ever mounting to call `onComplete`. Since `onComplete` is what flips `animate`/`isGenerating` back off, the message gets stuck showing as "still generating" forever. If you ever see a regenerated message stuck in that state, check whether something changed this key.

**`MessageActionsRow`'s action order is deliberate.** Copy always leads, regardless of sender — it's the one action every message gets. Refresh comes right after edit, ahead of the version-nav arrows it produces, so cause (regenerate) reads before effect (step through the resulting versions). The reply trigger is identified by a plain DOM `id` (`thread-trigger-${messageId}`), not a ref, so closing a thread can hand focus back with a simple `document.getElementById` lookup — the same approach `CommandPalette` uses for its active-option scroll-into-view.

**`ChatMessageRowContent` is genuinely shared, not copy-pasted, between the main pane and a thread.** A thread is just another list of the same `ChatMessage` shape, so the bubble/tool-call/questionnaire/streaming rendering only needs to exist once. The streaming-complete guard ("is this still the active streaming message?") lives in each pane's own `onStreamComplete` passed down as a prop, since the main pane and an open thread stream independently of each other — don't try to hoist that guard into `MessageRow.tsx` itself. `renderTrailing` and `editing` are only ever wired up by the main pane; a thread is a side conversation, not something you edit history in.

**A `null` `activeId` means "unsaved draft chat," and it collides with other `null`-initialized ids if you're not careful.** Each `useConversation` instance's `typingId`/`streamingId` both start as `null` before anything has ever generated. `isTyping`/`isGenerating` in `AiChat.tsx` guard with `activeId !== null &&` before comparing against `mainConversation.typingId` — without it, `null === null` would read as "typing" on every freshly opened draft chat, which is exactly the bug that shipped once before this guard existed. If you add another per-pane id-keyed comparison, give it the same guard.

**An attachment-only send has no text, but the API rejects an empty `message`.** `describeAttachments`/`promptText` in `messageHelpers.ts` exist so a message with files but no typed text still sends something meaningful (`"Attached: file.png"`) to the API and into history, while the chat bubble itself still shows just the attachment chips, no synthetic text. This applies everywhere a message's text is read for the API — send, regenerate, and history-building all go through `promptText`, not `m.text` directly.

**`types.ts` is re-exported from `AiChat.tsx`, not just defined there.** Your API routes and `ThreadPanel.tsx` import `ChatMessage`, `ChatEntry`, etc. from `AiChat.tsx`'s own path, not from `types.ts` directly — moving the type definitions into `types.ts` was an internal reorganization, and that import path had to keep working unchanged. If you add a new exported type to `types.ts` that anything outside this folder needs, add it to the `export type { ... } from './types'` line near the top of `AiChat.tsx` too, or code importing it from `AiChat.tsx` will fail.

**Don't add a settings-modal field "for completeness."** Four of them (response length, creativity, web search, sound) were added that way once and never wired to anything — each was read only by its own control, a closed loop contributing nothing. They were removed. `model`, `displayName`, and `autoTitleEnabled` earn their keep (displayed elsewhere, or feeding real title logic) — if a new field can't say the same, it's decoration, not a feature.
